# Build Roadmap

## Phase 0 — Discovery

Complete the brand questionnaire, collect approved brand assets and product inputs, resolve conflicts, approve the discovery brief, and lock the first-release component list.

## Phase 1 — Foundations

Create approved tokens, modes, Text Styles, Effect Styles, icons, logos, and mandatory Foundation guides.

For each Foundation item, create or update its mandatory guide immediately after its values, assets, or rules are ready. Do not ask a separate documentation question. Read [Documentation Visual Language](documentation-visual-language.md) before authoring the guide and reuse the established documentation pattern already approved in the target Figma file.

The visible guide contains a complete grouped reference of approved names, values, modes and individual usage with actual bound or measured specimens. Choose the body structure from the information instead of forcing one template: semantic lookup may use hierarchical mode tables, primitive scales may use swatch families, dimensions may use measured diagrams, visual systems may use specimen rows, and behavioral rules may use prose or comparisons. Add do-and-don't or comparison sections only when the owning specification requires a real designer decision.

Follow [Documentation Acceptance](documentation-acceptance.md); compare approved, implemented and documented sets before proceeding. A generic guide shell or a few examples cannot satisfy completion. Keep internal IDs and raw QA logs in the build ledger.

## Phase 2 — Atoms

Build and validate the smallest reusable controls and visual elements.

After each Atom passes internal component QA, ask whether to build its optional designer documentation. If approved, show its purpose, usage, actual public permutations, relevant decision examples, and concise accessibility status using the shared documentation visual language.

## Phase 3 — Molecules

Combine atoms into focused components such as fields, groups, menus, and feedback.

After each Molecule passes internal component QA, ask whether to build its optional designer documentation. If approved, show its purpose, usage, actual public permutations, relevant decision examples, and concise accessibility status using the shared documentation visual language.

## Phase 4 — Organisms

Combine atoms and molecules into larger reusable interface regions without product-surface categories.

After each Organism passes internal component QA, ask whether to build its optional designer documentation. If approved, show its purpose, usage, actual public permutations, relevant decision examples, and concise accessibility status using the shared documentation visual language.

## Phase 5 — Patterns and integration validation

Document recurring tasks and validate the building blocks together without introducing page-level deliverables.

## Phase 6 — Release

Run accessibility, naming, token-binding, visual, responsive, documentation-structure, and consumer-file checks. Publish in dependency order.
